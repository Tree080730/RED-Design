# 技术方案 Spec：Food Check Details 结果详情页

> 状态：已确认
> 创建时间：2026-09-25
> 对应需求：点击结果页 “Checking Details ›” 进入详情页，内容参考 PRD。

## 需求复核结论

- 目标：把当前不可食用结果的灰色详情文字改为明确可点击入口，并展示个人条件、演示依据与仍未知的信息。
- 用户链路：完成食物检查 → 出现 `Can’t Eat :(` → 点击 `Checking Details ›` → 进入详情页 → 返回结果页。
- 页面结构：固定 44px 顶栏；结果摘要；原因列表；依据与未知项；底部下一步操作。
- 内容模块：
  1. `Can’t eat` 结果摘要与 `Demo result` 标识。
  2. `Why`：按 Allergies → Dietary restrictions → Preferences 顺序列出当前选中条件与冲突状态，首要冲突突出，其余原因保留。
  3. `What we know`：区分 Demo 菜品资料、典型做法或图片线索；不把图片外观当作隐藏配料证据。
  4. `Still unknown`：保留交叉接触、隐藏调料等未确认信息。
  5. `Ask the restaurant` 下一步入口；本次先保留为后续沟通卡入口，不在详情页内伪造真实检测结论。
- 输入：当前选择的过敏、饮食限制和偏好；当前 Demo 结果；预设样例依据。
- 输出：可读、可返回的结果详情，不改变原结果动画或判断状态。
- 未确认信息：详情页具体英文短文案尚未逐页确认。本方案使用 PRD 语义的短句，所有食材与依据均明确标为 Demo data。

## 路径分诊

- 主路径：F 组合型需求（已有结果组件变更 + 新增业务页面状态 + Demo 详情数据）。
- 专项标签：组件库、工程、文档。
- 归类原因：需要把现有展示文字改为按钮，新增详情视图，并把当前选择传入结果详情；不增加真实识别服务。

## 复用策略

- 复用 token / 样式：品牌蓝、文字、边框、圆角、间距和按钮全部使用现有 `--ds-*` 变量。
- 复用页面模式：沿用结果页内部状态切换和统一顶栏，不引入路由库。
- 需要新增：`FoodCheckDetails.tsx`、页面样式、有限 Demo 详情数据及进入/返回状态。
- 明确不新增：真实 AI 识别、真实配方数据库、录音翻译、后端、第三方依赖。

## 风险与确认点

- 共享组件：不修改通用 SVG 嘴部组件；只复用统一顶栏和 Ant Design Button。
- 全局 token / 样式：不修改。
- 路由 / 状态 / 构建配置：不增加路由；仅扩展结果页局部状态与 props。
- 三方依赖：不新增。
- 设计系统偏离：无。
- 数据风险：当前食物和判断均为 Demo。页面必须显示 `Demo result`，并把未知项保留下来，不能表达为现实食物安全保证。
- 范围边界：`Ask the restaurant` 的中文沟通卡和模拟回复属于 PRD 后续步骤 09–10，本次只建立入口；若要求本次一并完成，需要追加增量分诊。

## 验收标准

- 操作入口：不可食用结果页的 `Checking Details ›`。
- 操作步骤：点击入口进入详情；查看原因、依据和未知项；点击返回回到原结果画面。
- 成功结果：
  - 入口是可聚焦、可点击的按钮，并有清晰 accessible name。
  - 过敏、饮食限制、偏好按 PRD 优先级展示，且不会遗漏同时存在的原因。
  - 依据来源和未知项可区分；页面包含 Demo 标识。
  - 返回后保留此前的不可食用结果状态，不重播整个检查流程。
  - 402×874 画布可滚动阅读且无横向溢出。
- 失败 / 降级结果：减少动态模式直接切换页面；未选择任何个人条件时不生成个人化原因，并提示无法给出个性化详情。
